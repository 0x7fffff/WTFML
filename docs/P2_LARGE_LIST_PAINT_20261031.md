# P2：大列表首绘 / 重列 / 滚动实测（2026-10-31）

「复杂预设/大列表」那一项要求**先测首绘、滚动和批量状态更新，再决定模型委托/虚拟化**。
这一轮只做测量和判据，不动列表实现：先量清楚时间到底花在哪一段，免得下一轮照着感觉选方案。

## 量的是什么

实例文件页（`ui/InstanceFilesPage`）是这一套里条目最多的列表（模组目录几百到几千个文件是
常态），它每一行是 `setItemWidget()` 摆上去的**真控件**，不是代理画的。测量用例进了
`tests/mw_check/ModActionPanelChecks.cpp`，由环境变量开关（默认不跑、不进断言）：

```powershell
$env:WTFML_FILES_PAINT_PROBE_ROWS = '1000'
./build/verification-mingw13/tests/mw_check/mw_check_mod_action_panel.exe
Remove-Item Env:WTFML_FILES_PAINT_PROBE_ROWS
```

四个数字（微秒）：

- `build_us`：`setDirectory()` 换到这一份目录 + 一次 `processEvents()`（扫盘 + 建行 +
  视图那一趟排版）；
- `refresh_us`：同一份目录再 `refresh()` 一遍（重扫 + 整表重建）；
- `scroll_us`：滚到底 + 一次事件循环（重绘那一截）；
- `filter_us`：搜索框敲一个字（筛到 111 条 + 重建）。

**只打印、不设阈值** —— 耗时跟机器走，写死数字只会变成一条噪声断言。以下都是本机
（offscreen，MinGW 13 构建目录 `build/verification-mingw13`）的数字。

## 结果

| 行数 | build_us | refresh_us | scroll_us | filter_us |
| ---: | ---: | ---: | ---: | ---: |
| 200 | 109,939 | 88,670 | 1,194 | 41,329 |
| 500 | 360,707 | 363,993 | 1,619 | 44,561 |
| 1000 | 1,536,874 | 1,323,290 | 2,972 | 52,667 |

（1000 行那两格在多趟里落在 1.28–1.54 s 之间，取其中一趟。）

三件事从这串数字里能直接读出来：

1. **滚动和重绘完全不是问题**：1000 行滚到底 3 ms 上下，跟行数几乎无关。
2. **钱花在"把行造出来并塞进列表"上**：200 → 500 → 1000 行是 0.11 → 0.36 → 1.3 s，
   行数翻倍时耗时翻了 4 倍多（超线性）。筛选到 111 行那一趟稳定在 40–60 ms —— 反过来说，
   耗时跟**建了多少行**走，跟屏幕上能看见几行走。
3. 一次 1000 行的整表重建里，`makeRow()`（QWidget + 两个布局 + 图标/名字/大小时间三格 +
   行尾按钮）与 `setItemWidget()` 各占约一半（一次重排下来约 0.3 s，逐段计时合计），
   剩下的在 `QListWidget` 把这一千个条目控件摆进视图那一趟。

顺手排掉了一个便宜的猜想：在重建循环外面套 `setUpdatesEnabled(false)` / 还原，**没有**
可测的差别（1.35 s → 1.34 s）—— 说明慢的不是"画"，是"造对象 + 条目控件登记"。所以这不是
调一个视图选项能解决的。

## 没做的

- **没有**改成模型委托 / 虚拟列表，也**没有**改成"只给可见范围建控件"。这两条都能把
  1000 行压到几十毫秒，但要动这一页的行构建、悬停露「详情」、开关、选择按身份还回去、
  统计异步补格、滚动锚点这些既有判据；超线性那一段也还没定位到具体哪一句（候选：
  `QListWidget` 条目控件激活、`refresh()` 开头那次 `clear()` 的销毁成本）。下一轮先定位
  超线性项，再在两套方案里选。
- 其余列表（预设管理、下载页版本树）行数通常小一个量级，本轮没测；不拿这一页的数字替它们
  下结论。

这一轮不改产品代码：`ui/InstanceFilesPage.cpp` 一个字节都没动（测量时临时插的计时随即
还原）。
