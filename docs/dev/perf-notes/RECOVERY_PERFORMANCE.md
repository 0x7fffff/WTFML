# 恢复与续装的响应性：把整份读文件的活移出界面线程

给改下载恢复、预设续装、恢复记录（receipt）的人看：这条路上哪些整份读文件/哈希/扫目录的同步活已经挪到后台、各自的约定、量到的数，以及还剩什么。2026-10-28 至 10-29 分九步完成。

## 通用约定

后台化的每一步都遵守这些，改这些代码时保持：

- **单作业 + 代次 + 取消令牌**：每个控制器最多一个校验作业；取消、销毁、开新一批会换代次和令牌，已在跑的作业回来时按代次丢弃结论。控制器销毁使取消标记生效，已销毁对象收不到完成回调。
- **后台只拿值，不碰 UI**：只读条目/目录副本和共享取消标志，不捕获 MainWindow / 控制器，不碰 `m_checkpoint`；登记、发信号一律回界面线程。
- **哈希不降级**：完整 SHA-256 / 必要 SHA-1，不以大小或修改日期代替；按 1 MiB 分块读，每块查取消标记；不接受部分快照。
- **恢复条件在作业结束后重查**：回到界面线程再确认下载器忙态、批次身份、实例是否运行、目标/预设指纹，通过才调用原来的安装接续。恢复方法返回 `true` 只表示"接受校验"，不是校验或安装已完成。
- **恢复记录的锁持续保留到校验收尾**，后台校验期间不重写它；关闭窗口/退出保留记录供下次明确恢复，明确取消才清理。
- **校验期间只提供取消**，不提供暂停（暂停按恢复记录重放，而没核对完的文件连原件指纹都没进记录，允许暂停等于静默丢掉它们）。界面阶段提示显示"正在校验恢复文件"/"正在后台校验下载目标"。
- 检查与实际提交之间仍有外部进程竞态，也不保证失联硬盘的系统读取能立刻返回；后台化不减少总读盘量。

## 各步要点

**①–⑥ 共性**：每步都新增 32 MiB 文件夹具场景，覆盖正常继续、取消、销毁、恢复条件撤回、外部修改；所有接口和目录都是隔离的本机夹具，不碰真实账号、原游戏目录，也没有运行真实 Java 安装器。核对期间 `canPauseBatch()` 为 false。

- ① 取消不调用安装接续；原恢复记录的锁保留到校验收尾。
- ③ 无法确认目录时明确失败；取消或对象销毁不再继续下载/部署。
- ④ 用户取消的原任务保持"已取消"，不会被完成回调改成失败；清单/元数据读取仍同步。
- ⑤ 公开的同步 `resumeBatch()` / `restoreBatch()` 仍在，但生产接线不再调用它们（界面"继续"走 `DownloadBatchController::resume()` → 后台校验 → `resumeValidatedBatch()`），只剩测试在用，所以 `resumeBatch()` 提交前那一趟同步 `unchanged()` 不构成界面卡顿。
- ⑥ MainWindow 私有接续入口默认仍同步核对；只有生产恢复回调在后台检查通过后用已校验入口，避免重复扫描。"原件读不到且保存指纹为空"被拒绝，不再把两个空对象当成未变化。

**⑦ 跳过校验**：`DownloadManager::scheduleFile()` 原来对每个已存在的目标当场做两件整份读文件的活：`fileAlreadyValid()` 的 SHA-1 和 `DownloadCheckpoint::fingerprint()` 的 SHA-256。重装一个装过的实例时几千个文件都在盘上，这两趟加起来就是"点了下载、窗口几十秒不动"。现在 `precheckReadsFileBody()` 只回答"这一份要不要整份读"：点名 / 不在盘上 / 0 字节 / 只看存在 / 大小一眼不符（且不需要指纹）在界面线程当场问完，行为与从前逐字一致；要读的装成 `PrecheckJob` 进单工作线程池，结论回界面线程才记账。判据后半段抽成 `fileBodyValid()` 一处，`fileAlreadyValid()` = 便宜的闸 + `fileBodyValid()`，后台调同一个函数。

- 记账推迟到结论回来，之前这份既不算跳过也不算要下；`isBusy()` 与 `checkAllDownloadsFinished()` 把队列和在跑的算上，否则会在没核对完时发出批次完成。
- `clearPrecheckJobs()` 换代次和取消令牌；带令牌的 SHA-1 按 1 MiB 分块读，不带令牌的老路逐字不变，哈希算法仍只有一份。
- 新增 25 条断言：判据真值表（大小/哈希/未知哈希/不存在/zip 头）、调度返回时尚未记账、32 MiB 已正确文件后台核对后被跳过且零请求、坏文件顺手算出的原件指纹逐字落进恢复记录、取消后零请求且忙态自行落下、文件不在时仍是同步判决。

**⑧ 恢复记录**：`tests/core_modules/DownloadReceiptScaleTests.cpp`（`wtfml.core-downloads` 的 DRS 一节）按上限造 50,000 条记录真存真读，全部同步，就是界面线程那一趟。

| 段 | 改前 50,000 条 | 改后 50,000 条 | 5,000 条（改前 / 后） |
| --- | --- | --- | --- |
| `save()` 整趟 | 1,335,363 µs | 342,247 µs（−74%） | 46,901 / 42,146 µs |
| `load()` 整趟 | 1,413,487 µs | 404,375 µs（−71%） | 46,920 / 46,921 µs |
| 盘上 | 22.3 MB | 1,347,068 字节（−94%） | — / 135,196 字节 |

改前 `WTFML-PROTECTED-1` = DPAPI(明文 JSON)，其中 DPAPI 加密 1,054,944 µs（79%），搭 JsonArray / 转 Compact 170,677 / 120,603 µs，原子写 14,451 µs。DPAPI 按字节数收钱，而 JSON 九成是重复键名：`qCompress(plain, 1)` 35 ms 压到 1,346,853 字节（十六分之一），加密只剩 8 ms。现在写 `WTFML-PROTECTED-2` = DPAPI(zlib 压缩的 JSON)，读侧两档都认。

- `DownloadCheckpoint::encodeReceipt()` 是写侧唯一出处；压不小的小清单照写 `-1` 那档，不会为了格式统一写更大的。
- 注意：读侧剥掉 `-2` 后必须把 `-1` 魔术接回去再交给 `TokenStore::unprotect()`，它按魔术分"DPAPI 解"和"老混淆解"，不带魔术会被当老格式解出乱码（第一版就这么错，DRS6 当场红）。
- 老那档（用户盘上暂停中的批次）继续读得了（DRS12 用手写 `-1` 夹具验）；解不开就 `load()` 回 false、原件不动（DRS10/DRS11）；原子写与 DPAPI 失败照旧让 `save()` 回 false；`QSaveFile` 落盘仍在退出前同步完成。
- 剩下的 `load()` 里 JSON 解析约 64 ms，逐条校验（每条 `QUrl(StrictMode)` + `cleanPath`）约 270 ms @ 50k、27 ms @ 5k。这是认不认记录的门，没动。恢复记录的存/读仍同步，这次是从 1.3 s 压到 0.34 s，不是挪走。

**⑨ 首装快照**：第一份文件开始下的那一刻（`DownloadManager::beginBatch()` → `batchStarted` → `DownloadBatchController`）原来同步走目标实例的配置目录（`options.txt` / `optionsof.txt` / `servers.dat` / `config/` / `defaultconfigs/` / `resourcepacks/` / `shaderpacks/` / `wtfml.datapacks/` / `datapacks-pending/` / `saves/<世界>/level.dat` 与 `datapacks/`），整文件算 SHA-256（`Presets::snapshotInitializationTargets`）。`tests/core_modules/PresetSnapshotScaleTests.cpp`（模块 `presets`，PSS1–PSS4）：

| 树 | 格数 | 走一趟 |
| --- | --- | --- |
| 常见的整棵树（400 份 config、40 份 defaultconfigs、2×4 MB 资源包、2 MB 光影包、带 80 份函数的数据包存档） | 559 | 493 ms |
| 只有一份 64 MB 资源包 | 11 | 285 ms |
| 空实例 | 10 | 7.7 ms |

恢复那条路再走一遍同一棵树（`unchangedInitializationContinuation`）521 ms，已在第⑥步挪进后台，所以只有首装这一趟在界面上付钱；代价按字节线性，资源包/光影包动辄几十上百 MB。

改法：批次开门只登记便宜的几格（版本意图 + 预设 id + 预设指纹），`presetTargets` 那棵树挪到后台。

- `MainWindow::snapshotDownloadContinuation()` 不再拍这棵树；`DownloadBatchController::setContinuation()` 多一个第四个回调（`std::function<QJsonObject(const QJsonObject &, const std::atomic_bool *)>`），用意图里的 `root` / `instance` 去拍，与恢复判据用同一个表达式。
- `DownloadBatchController::requestContinuationTargets()` 只在"写了预设 + 有实例名"时发这一拍（服务端安装的意图没有 `instance`，不靠这一拍）；算完先核代号没变、`m_current` 还是这一趟、恢复记录还是同一份路径，才把 `presetTargets` 并进去。
- 落盘走 `DownloadManager::updateCheckpointContext()`：只换 `context` 并当场 `save()`，不碰 `dirty`（那是文件表的账）。
- 拍不出来（路径有关口、文件读不动）则整条接续意图置空，这一批按普通下载收尾。留半截（有预设、没 `presetTargets`）会在恢复时被 `unchangedInitializationContinuation` 挡下，只会让"接着装"出现一个按不动的按钮。

对照（`tests/mw_check/DownloadBatchChecks.cpp`，`MEASURE preset-targets`，302 份小文件的树）：同步走一遍 88.6 ms，现在只登记意图 3.7 ms；剩下的 3.7 ms 是建记录、写盘一次。

## 意外发现

- ① 首轮 `20261028-123514-d38777ad` 4/5：夹具没有先结束旧任务，恢复加载按设计建立了另一任务，夹具却继续操作旧 ID。改为模拟旧进程退出后断言原 ID 被接回，生产身份规则没动。
- ④ 真实控制器测试发现产品问题：实例识别名 `fabric-loader` 与平台名 `fabric` 不一致，正常发行版被当成缺失。现在统一 Fabric/Quilt 别名（用于预设约束、平台查询、计划匹配），未知名称不猜，真正不同的加载器仍拒绝。测试失败时提前自销毁的安装器改用 `QPointer` 避免悬空访问。该步另有两次编译失败（缺声明/头文件）和一次受限环境下本机测试服务没进入下载阶段、随后段错的记录，后者换到允许本机接口的环境重跑。
- ③ 首次命令误填模块键，运行器在开始测试前拒绝，更正为 `presets`，判据没改。
