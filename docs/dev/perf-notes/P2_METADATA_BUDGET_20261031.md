# P2 元数据请求预算（2026-10-31）

## 本轮范围

`net/ControlGet.hpp` 提供非阻塞的元数据 GET 作业。游戏侧五类加载器版本查询及服务端 Fabric/Quilt 安装器查询接入既有 `RequestBudget::Lane::Control`，与 `HttpClient` 共用四个短请求名额；大文件仍使用 Bulk 通道。保留用户设置的代理与原有来源，不把请求名额解释成 TCP/Java 连接上限。

- 无名额时等待，不阻塞界面；排队和传输计入同一尝试的截止。
- 加载器每次来源尝试仍为 30 秒，服务端安装器为 15 秒。NeoForge 原有一次镜像回退保留；回退是新一次尝试，不声称整条查询仅 30 秒。
- 切换游戏版本/加载器、显式取消或销毁页面会撤销排队作业；已发出的请求中止，不产生用户取消导致的旧列表错误。
- 每次查询保留代次，旧响应不能覆盖新选择。完成、失败、取消和回复销毁均归还额度，完成回调前先归还名额。
- 元数据正文最多积累 2 MiB，避免异常列表无界缓冲；不用于文件正文下载。成功结果仍由原解析器读取，既有摘要/安装流程不变。
- 诊断属性 `wtfmlControlQueuedMs` 记录排队耗时；绝对截止保留 `wtfmlControlDeadlineExpired`，不会把超时误判成用户取消而破坏既有镜像回退。

## 验证

专项位于 `tests/mw_check/RequestBudgetChecks.cpp`：跨两个 QNAM 的八次真实本机 HTTP 请求、Control 额度耗尽、排队超时、释放后继续、删除排队作业/页面、活动请求取消、传输绝对截止及 VersionManager 换版本取消。网络四组回归 4/4 通过（80.06 秒），记录在 `build/test-runs/20261031-005941-ee57bd98/`。

随后扩展网络管理器销毁场景，首次发现回复先于 QNAM 的 `destroyed` 通知销毁，导致过早取消回调；原失败保留于 `build/p2-metadata-final-test.log`。修正为回复销毁时立即还额度、取消回调下一轮确认，管理器销毁时撤销回调。最终专项 1/1 通过（9.30 秒），见 `build/p2-metadata-fixed-test.log`，包含持续小流量不绕过绝对截止，以及 QNAM 析构后继续处理事件仍无旧回调。本地 Release 构建通过。

这些是本机 HTTP 行为与生命周期验证，不是其它代理环境、真实上游 429 或所有网络客户端验收。

## 仍未覆盖

这次只收口上述版本查询，不代表所有独立 QNAM 都接入额度；2026-10-31 预设兼容的
Modrinth / CurseForge 版本表也已迁到同一档（见 [兼容查询预算](P2_COMPAT_BUDGET_20261031.md)），
皮肤那三发（档案、贴图、随机皮肤列表）同样已迁（见 [皮肤请求预算](P2_SKIN_BUDGET_20261031.md)），
资源商店那九处（搜索、版本表、项目、文件反查、精确前置、检查更新、图标）也已迁完，
`ControlGet` 顺带加上了带正文的 POST，见 [资源商店请求预算](P2_RESOURCE_BUDGET_20261031.md)；
服务端安装、加载器安装与 Java 管理的元数据同样已迁，见
[安装与 Java](P2_INSTALL_BUDGET_20261031.md)。至此元数据层不再有自己管超时的请求。
没有增加每来源 FIFO 或速率限制，也不把并发名额当作 429 的完整解法。
签名 URL 过期/表示变化的额外实网样本、多网络对照仍留在主计划（分段协调器的持续低速
比较已接入，见 [高速下载](../../features/HIGH_SPEED_DOWNLOAD.md)）；不同网络的速度不从本机 HTTP
夹具推导。
