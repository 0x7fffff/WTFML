# P2：大列表首绘 / 重列 / 滚动实测与修法（2026-10-31）

「复杂预设/大列表」那一项要求**先测首绘、滚动和批量状态更新，再决定模型委托/虚拟化**。
第一轮只测不改；这一版把量出来的那一处修掉了 —— 修的是"什么时候挂行控件"，不是列表
本身的写法。

## 量的是什么

实例文件页（`ui/InstanceFilesPage`）是这一套里条目最多的列表（模组目录几百到几千个文件是
常态），它每一行是 `setItemWidget()` 摆上去的**真控件**，不是代理画的。测量用例进了
`tests/mw_check/ModActionPanelChecks.cpp`，由环境变量开关（默认不跑、不进断言）：

```powershell
$env:WTFML_FILES_PAINT_PROBE_ROWS = '1000'
./build/verification-mingw13/tests/mw_check/mw_check_mod_action_panel.exe
Remove-Item Env:WTFML_FILES_PAINT_PROBE_ROWS
```

四个数字（微秒）：

- `build_us`：`setDirectory()` 换到这一份目录 + 一次 `processEvents()`（扫盘 + 建行 +
  视图那一趟排版）；
- `refresh_us`：同一份目录再 `refresh()` 一遍（重扫 + 整表重建）；
- `scroll_us`：滚到底 + 一次事件循环（重绘那一截）；
- `filter_us`：搜索框敲一个字（筛到 111 条 + 重建）。

**只打印、不设阈值** —— 耗时跟机器走，写死数字只会变成一条噪声断言。以下都是本机
（offscreen，MinGW 13 构建目录 `build/verification-mingw13`）的数字。

## 第一轮：修复前的表

| 行数 | build_us | refresh_us | scroll_us | filter_us |
| ---: | ---: | ---: | ---: | ---: |
| 200 | 109,939 | 88,670 | 1,194 | 41,329 |
| 500 | 360,707 | 363,993 | 1,619 | 44,561 |
| 1000 | 1,536,874 | 1,323,290 | 2,972 | 52,667 |

（1000 行那两格在多趟里落在 1.28–1.54 s 之间，取其中一趟。）

三件事从这串数字里能直接读出来：

1. **滚动和重绘完全不是问题**：1000 行滚到底 3 ms 上下，跟行数几乎无关。
2. **钱花在"把行造出来并塞进列表"上**：200 → 500 → 1000 行是 0.11 → 0.36 → 1.3 s，
   行数翻倍时耗时翻了 4 倍多（超线性）。筛选到 111 行那一趟稳定在 40–60 ms —— 反过来说，
   耗时跟**建了多少行**走，跟屏幕上能看见几行走。
3. 慢的不是"画"：在重建循环外面套 `setUpdatesEnabled(false)` / 还原，**没有**可测的差别
   （1.35 s → 1.34 s）。

## 三档对照：超线性在 `setItemWidget()` 与 `addItem()` 的**交错**里

把重建循环临时做成三档（环境变量开关，量完即删），1000 行：

| 档 | 建了什么 | item_us | make_us | set_us | build_us |
| --- | --- | ---: | ---: | ---: | ---: |
| 0 | 只 `addItem`，不建行控件 | 86–147 | 0 | 0 | 7,496 |
| 1 | `makeRow()` 建出来、随即删掉、不挂 | 1,121–1,597 | 46,590–50,147 | 8,307–8,992 | 67,808 |
| 2 | 正常（逐条 `setItemWidget` 夹在 `addItem` 中间） | 1,016,021–1,046,945 | 107,526–110,769 | 163,922–174,955 | 1,340,670 |

（`item_us` = `new QListWidgetItem` + `addItem`；`make_us` = `makeRow()`；`set_us` =
`setItemWidget()`。）

第 2 档那 1.0 s 落在 **`item` 那一段**：`setItemWidget()` 挂上一条之后，视图后面每一次
`addItem()` 都要替**已经挂着的那一整摞**重算一遍几何 ⇒ 第 k 条 item 的插入要给前面 k-1 个
行控件各算一遍，整表平方级。`makeRow()` 本身只占约 110 ms。

## 修法：先排完 item，再一趟挂控件

`rebuildRows()` 现在分两步：循环里只管"item + 行控件都建出来、配好对"，出了循环再逐条
`setItemWidget()`。同一版二进制 A/B（1000 行，`WTFML_FILES_ATTACH=9` 那一档就是旧写法）：

| 写法 | item_us | make_us | set_us | build_us |
| --- | ---: | ---: | ---: | ---: |
| 夹着挂（旧） | 1,049,113–1,056,008 | 111,921–115,017 | ~2 | 1,392,085 |
| 先排后挂（新） | 1,279–1,584 | 79,609–84,539 | 148,935–169,266 | 285,695 |

修完的表：

| 行数 | build_us | refresh_us | scroll_us | filter_us |
| ---: | ---: | ---: | ---: | ---: |
| 200 | 46,319 | 45,888 | 1,070 | 27,207 |
| 500 | 126,035 | 128,210 | 1,571 | 30,007 |
| 1000 | 285,695 | 311,942 | 4,173 | 39,915 |

1000 行 1.39 s → 0.29 s（约 4.9×，同一版二进制 A/B）。

## 还剩下的

- `makeRow()` 那 ~80 ms/1000 行：每行 ~10 个控件，这部分只能靠委托画或只给可见范围建。
- 先排后挂之后 `setItemWidget()` 那 ~150 ms 仍是平方级（每次挂都要遍历全部已挂控件重算
  几何）。试过 `setUpdatesEnabled(false)` 无效、`m_list->hide()` 降到 111 ms、先
  `doItemsLayout()` 无效 —— 都不值得为这点再改一处状态。
- **没有**改成模型委托 / 虚拟列表：会动行构建、悬停露「详情」、开关、选择按身份还回去、
  统计异步补格、滚动锚点这些既有判据（`itemWidget()` 本身是这一页和测试在读的接口）。
  等这一页之外的列表也真出现 1000 行级的目录再说；其余列表本轮没测，不拿这一页的数字
  替它们下结论。

测量时临时插的三档开关和分段计时已删；产品代码只留"先排后挂"这一步。

## 同一条规矩：游戏规则表（WorldSettingsPage）

`rebuildRuleRows()` 原来是 `addItem()` + `setItemWidget()` 夹在同一个循环里 ——
正是上面那个平方级写法。这一页每换一个世界、每改一次搜索框（200 ms 防抖之后）都要
整表重摆，而每条规则都有一个行控件（开关或输入框），模组世界几百条规则时最看得出。

现在和文件页一样分两步：循环里建 item 与行控件、先配上对，出了循环再逐条
`setItemWidget()`。**这一页没有单独测量**：没有为它加探针（不想为一次改动在产品代码
里留一行分档开关），所以这里只记"写法同一条"，不拿文件页的数字替它下结论。行为由
`ui_check` 的 Z16 一段和 `mw_check` 的存档页用例覆盖，两套全绿。
