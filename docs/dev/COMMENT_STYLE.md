# WTFML 注释规范

本文档规定 WTFML 代码注释的撰写与维护原则，供所有参与代码开发的成员使用。核心目标是记录「为什么这样写」与「关键约束」，避免复述代码字面逻辑。

---

## 1. 核心原则

注释的核心价值在于阻止后续开发中的误改与误操作。

### 应当记录

- 复杂算法、网络协议或特定数据格式的**原理与关键步骤**；
- 易引发疑问的**设计考量**、历史兼容原因及 Windows 平台特例；
- 容易踩坑的**边界条件、执行顺序、线程模型、所有权与生命周期**；
- 公共 API 的**参数含义、返回值语义、失败行为与前置假设**；
- 无法直接从代码推导的**产品硬约束**（安全边界、不可逆文件操作、内存与性能预算）。

### 避免记录

- 机械翻译函数名或变量名的废话；
- 每一行代码伴随的字面控制流说明；
- 缺乏上下文的个人缩写；
- 已过时的设计或与现有代码矛盾的历史记录；
- 临时开发日志、单次测试结果与截图流水。

---

## 2. 文件头规范

每个 `.hpp` / `.cpp` 建议保留简明文件头：

```cpp
/**
 * @file Theme.cpp
 * @brief 主题令牌、调色板与样式表的计算与铺开。
 * @note 任何新增颜色都应从令牌派生，不要在页面里另写一组近似色。
 */
```

- 包含 `@file` 与 `@brief`。
- 存在跨模块或跨文件硬约束时补充 `@note`。
- 变更记录由版本控制系统承载，文件头不堆砌提交历史。

---

## 3. 行内注释与正反示例

### 推荐保留：记录关键约束与原因

```cpp
// Xms 必须 <= Xmx；否则 JVM 在初始化阶段直接退出：
//   Initial heap size set to a larger value than the maximum heap size
// 所以先夹下限再夹上限，不能直接 qBound(512, value, xmx)。
```

```cpp
// 此处必须使用 QPointer：follow() 回调可能触发子控件重建，
// 原裸指针在回调期间可能失效。
```

```cpp
// 配置文件写入必须使用 QSaveFile：目标可能为用户已有配置，
// 避免写入中断时导致文件损坏。
```

### 推荐清理：复述代码字面行为

```cpp
// 设置最大内存（反例：函数名已自解释）
setXmx(value);

// 如果为空则返回（反例：控制流显而易见）
if (path.isEmpty()) return;

// 2026-09-28 改成这样，因为当时测试红了（反例：过程流水非长期维护信息）
```

### 长注释处理

- 当单个原因解释超过 10 行时，先在首段给出 2–4 行核心结论，细节移至对应技术文档或函数实现处。
- 必须明确写清**风险是什么、触发条件、正确操作方法**。

## 4. 类与接口注释

公共类、公共接口及关键信号/槽采用 Doxygen 格式注释：

```cpp
/**
 * @brief 按当前系统内存建议最大堆（MB）。
 * @param totalMb 物理内存总量；<= 0 表示读不到。
 * @param availableMb 当前可用内存；<= 0 表示读不到。
 * @param modCount 实例模组数；<= 0 表示原版/未知。
 * @return 永远 >= 256，且不会超过 totalMb / 2 与自动档上限。
 */
static int suggestXmxMb(qint64 totalMb, qint64 availableMb, int modCount = 0);
```

- `@brief` 使用中文；同一文件内参数与返回值描述语言保持一致。
- 聚焦调用方需要知晓的契约，包括边界值、空指针处理、异常路径与线程限制。

---

## 5. 标记规范

统一采用三种标准前缀：

- `// TODO:` 明确待办事项，必须注明完成判据；长期需求排入主计划。
- `// FIXME:` 已知缺陷，写明触发条件与未直接修复的原因。
- `// NOTE:` 关键约束与排错提示，阐明特定写法的原因。

---

## 6. 清理注释的流程

1. 查阅代码与对应测试，确认注释阐述的行为依然准确。
2. 聚焦注释本身，不混入无关的重构或逻辑修改。
3. 遇到不确定是否具有约束价值的注释，予以保留并标记待确认。
4. 提交时简要说明精简与移除的注释类型。

---

## 7. 语言与格式

- 保持项目现有的中文注释风格。
- 文本文件编码统一为 UTF-8。
- 遵循 `.clang-format` 格式化配置。
