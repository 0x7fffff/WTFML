# 数据目录占用与世界导入

## 同目录单窗口

产品启动时，在主窗口和日志文件建立前取得当前游戏目录及自带回退目录的锁。
同一目录已被另一份启动器占用时，提示并退出；锁创建失败也不继续写入。
切换到其它游戏目录、删除目录、复制实例到其它游戏目录时同样先取锁。

锁文件位于系统临时目录，使用解析路径别名和 junction 后的路径哈希命名，
不向游戏目录里添加锁文件。活进程的锁**不**因时间过长而失效：Qt 判陈旧的第一道是
"那个 PID 还在、且进程名对得上"，这一道永远优先于时间。异常退出（崩溃、任务管理器结束、
断电）留下的锁则靠 `QLockFile` 的过期时间接管 —— 这个值**必须**大于 0（2026-11-04 修正：
以前写的是 0，而 Qt 的 `isApparentlyStale()` 在 `staleLockTime == 0` 时**永**不判陈旧，
于是死 PID 的锁会一直把这个数据目录锁死；实测一台机器上积了 6 个）。现在取 60 秒：只
在崩溃之后让用户最多等一分钟，不会误伤正在运行的那一份。
拿不到锁时提示里会带上**锁文件的完整路径**，并说明"确认没有别的窗口在运行就删掉它" ——
那串名字是 SHA-256，不指路用户就只能重装。
不要手工删除另一份**仍在运行**的启动器的锁。

本进程取得的锁保留到退出，而不是切换目录立即释放：旧目录仍可能有后台任务或游戏会话。
不同启动器副本、互不重叠的数据目录可分别运行。此保护不约束游戏、同步软件或外部编辑器。

## 共用同一棵全局设置

装在两个目录的启动器各有自己的数据目录，但 `HKCU\Software\WTFML\WTFML` 是按机器共用的
同一棵注册表。整份写回会交错覆盖：甲只改了标题、乙只改了内存，谁后保存，谁就把对方刚改的
那一项打回自己启动时读到的旧值（用户看到的是"我改的那份没了"）。所以设置层按**逐项**写：

- `LauncherSettings::save()` / `GlobalJavaSettings::save()` 只写与 `load()` 快照不同的项；
  一项都没改时一个字节都不写 —— 未改过的默认值不会在首次保存时覆盖其它窗口，其它窗口
  删除某项以恢复默认时，当前窗口保存别的项也不会把被删项复活。
  **同一项**两边都改，仍然后写者赢（那是一件事的两个答案，没有可合并的余地）。
  写入失败（`QSettings::status()` 不是 `NoError`）不推进“已保存”基线，下一次保存会重试；
  不把失败当成已生效。
- 账号当前身份（`Account/…CurrentUuid`）、令牌和工具箱那几项本来就各写自己那一格，
  不存在"手里有一份旧列表、整份盖回去"的形状。
- 主题（`Theme::save()`）也改成了逐项写：`load()` 记下盘上原值以及包含默认值的语义基线
  （连同那份配置文件的身份），`save()` 只写和它不一样的项；"上一次设过、这一次没设"的项照样删掉
  （不删的话改回默认、重开一次又复活），但只删**盘上还是我们当初看到的那个值**的项 ——
  别的安装目录刚改成另一个值就别插手；**未知（未来版本）主题键保留**，不顺手清理。
  写入失败不推进保存基线。没有基线（这个进程还没 `load()` 过，或者换了配置文件）时退回老规矩：
  整组清掉重写。两个安装目录同时改**同一项**仍然后写者赢，没有可合并的余地。

这一条只保证"互不相干的项不会互相打回去"，不把两个进程对同一项的并发写变成合并；
也不是对所有历史跨目录写入口的并发审计。

## 真实双进程验收

`tools/acceptance_directory_boundary.py` 是人工验收入口，不进 CTest：它需要真实 Windows 桌面，
会启动两份**真实产品进程**（不同 exe 目录、共用同一份 `HKCU\Software\WTFML` 与同一个数据根）。
产品约定是同一数据根只开一个启动器窗口，所以第二个进程只允许出现拒绝对话框。脚本验证它停在
「启动器已在运行或目录不可用」对话框、不创建主窗口、不截断 `logs/wtfml.log`，
关掉对话框后以 1 退出；第一份窗口始终存活，最后正常关窗。脚本运行前会拒绝已有启动器进程，
并把标题临时钉回产品默认；结束时恢复借用的 `Launcher/CurrentFolder` / `Launcher/TitleText`
并清理临时安装目录。

本机 2026-10-24 实跑（Release 构建、Qt 6.10.1）：10/10 断言通过，第二个进程没有主窗口、
没有截断日志、关掉拒绝对话框后以 1 退出，第一份窗口始终存活。原始用法见
[docs/TESTING.md](TESTING.md) 的人工验收探针一节。这是真实产品双进程证据，不是用测试程序里的
独立锁子进程代替。

## 「目录被占用」与「文件被占用」的区别

两条错误长得像，处理办法完全不同，界面上必须说清是哪一条：

- **目录被占用**：另一份启动器进程已经持着这个数据目录的生命周期锁。提示原话是
  「这个数据目录已被另一份启动器占用，请先关闭那一份窗口。」这时**整个启动器不该继续
  写入这个目录**，用户要做的是关掉另一份窗口（或换一个游戏文件夹），不是重试。
- **文件被占用**：目录锁是我们的，但某个具体文件被游戏、同步盘或杀毒软件开着
  （Windows 上是共享冲突）。症状是单个操作失败（改名、删除、发布备份、写配置），
  提示应指向那个文件或那一项操作，例如「文件被游戏占着」；用户要做的是退出游戏/同步
  程序后重试那一项，**不需要**关启动器。删除世界这类已经无法回头的操作照实报失败，
  不假装成功。

  这一条现在是判据，不只是约定（2026-10-24）：夹具用一个 `dwShareMode = 0` 的 Win32 句柄
  拿住树里的一件文件，等价于「游戏还开着」。`ZJ6` 验世界改名/导入——失败时旧的那一份原样在、
  新名字没被造出来、导入的暂存收拾干净；`ZAO6` 验整棵进回收站——`moveToRecycleBin()` 回
  `false` 且带原始 HRESULT，被占着的那一件还在原处、大小没变，放开后逐字节仍是原样，
  同一棵放开后照常进去。

  和它平行的一类是**权限失败**（不是有人占着，而是根本不许做）：`ZJ7` 给 `saves/` 挂一条
  拒绝写/追加的 ACL（`icacls /deny …:(WD,AD)`，拒绝项压过允许项，管理员也绕不过），
  导入世界照实失败且不留半截、源一个字节不动、权限放开后同一趟成功；`ZJ8` 把拒绝项挂到
  **源里**那一件上（`/deny …:(RD)`），要求失败话术由 `copyTreeWithoutFollowingLinks()` 的
  首因点名那一件与阶段（`文件复制失败` / `无法打开源或临时文件`），同时不发布、不留暂存；
  `ZAO7` 反过来钉住「删不掉 ≠ 权限不够」——删除只需要 `DELETE`，那一件不许写也照样进回收站。
  `ZAP1` / `ZAP2` 补上另一半：**「删除没有权限」本机造得出来**，夹具挂两条拒绝项
  （那一项 `(DE)` + 它所在目录 `(DC)`）。2026-10-24 记的那条「只能靠真机验」是错的：
  Windows 判一项能不能删是「自己身上有 `DELETE`」**或**「所在目录有 `FILE_DELETE_CHILD`」
  二者其一，只挂 `(DE)` 时父目录那条 `DC` 还在，实测照样删得掉；两条一起拒才挡得住。
  现在 `moveToRecycleBin()` 动手之前先用 `CreateFileW(path, DELETE, …)` 预检一次：
  `ERROR_ACCESS_DENIED` 说「权限不允许删除」，`ERROR_SHARING_VIOLATION` 说「被别的程序
  占着」，两种原因不再混在「回收站不可用、放不下、或者被占着」那一句里。预检还有个
  副作用是**一个字节都不动** —— 让 `IFileOperation` 自己去撞的话，它会先把子树里删得动
  的搬进回收站、最后才在目录那一层失败（实测：里面的文件没了、目录还在），`ZAP1` 钉的
  就是「里面那件还在原处、内容没变」。

不要把两者合并成一句「目录正被使用」：那会让用户在两份启动器都关掉之后仍然不知道
是游戏还开着；反过来，把文件冲突说成「另一份启动器占用」会让他去关一个不存在的窗口。

## 写入口审计（2026-10-22）

判据：写到「当前游戏数据根 / 启动器默认数据根 / `versions`、`Servers` 所属根」里的用户数据，
必须先过 `WriteDirectoryGuard::acquire()`（它把路径归并到数据根）。`ServerWriteGuard` 和直接调
`DirectorySessionLock::acquire(AppPaths::minecraftDir())` 用的是同一把键，算等价。
审计覆盖 `src/` 下所有 `QSaveFile` / `QIODevice::WriteOnly` / `QFile::copy` /
`QDir().mkpath` / `QFile::rename` 的 54 个文件：

- **显式取锁 35 个**：实例复制/移动/删除/改名/元数据、导入、备份/还原/中断恢复、版本与文件修复、
  服务端注册/配置/玩家名单/EULA、预设库与预设应用/提取/模组安装、世界导入/移动/`level.dat`、
  升级事务、任务/启动历史账本、实例分组、服务器列表、更新策略、Java 别名目录、启动日志等。
- **不取锁且可接受 17 个**：用户自选导出路径（整合包、日志、崩溃报告、主题、哈希清单）、
  可重建缓存（图标、皮肤缓存、默认皮肤、服务器状态、主题背景、预览资源）、诊断日志。
  写的是"丢了再生成"的东西，或者根本不在数据目录里。
- **本轮补上的缺口**：`GlobalJavaSettings::downloadJavaRuntime()` 与
  `downloadJavaFromMojang()`（建目录、解压运行时之前取根锁；拿不到就不写）、
  `PresetApply::makeBackupDir()`（备份落在预设库那一头，单独取锁；拿不到就让整趟停下）。

只由已取锁调用方驱动的写函数（`LocalFileReuse`、`ResumableDownload`、`ZipUtil`、
`DataPackPreset`、`GenericFiles`、`MalilibKeys`、`ServerListPreset`、
`FolderManager::copyTreeWithoutFollowingLinks`）按调用方记账：**新增调用方必须自己先取锁**。
这条审计只看"写入口有没有取锁"，不代表每个入口的路径边界（junction、大小写、越界）都已复核。

## 路径边界复核（2026-10-24）

和上面那份清单是两件事：上面问"写之前有没有取锁"，这里问"**这条路径最终落到哪儿、
中间经过哪儿**"。分三层，各自只有一个出处：

1. **名字那一段**：所有拿用户输入或清单里的名字去拼路径的地方，逐段过
   `InstanceFiles::validatePathSegment()`（分隔符、`<>:"|?*`、控制字符、`.`/`..`、
   结尾点与空格、Windows 保留设备名）。整合包里那一条相对路径走
   `ModpackImport::isSafeRelativePath()`，内部也是它。
2. **最终落到哪儿**：`InstanceFiles::pathIsSameOrInside()`（解符号链接、8.3 短名、
   大小写，再解 junction）。实例复制/移动、世界导入、升级事务、备份还原、暂存目录、
   目录锁键都用它。
3. **中间经过哪儿**：`InstanceFiles::pathHasLinkComponent()`。最后那一件文件自己不是
   链接时，第 1、2 层都看不出来 —— 危险的是它上面某一层（`config/`）整根指着别处。
   判据来自它的四个写入口：MultiMC patches、跨实例传输、数据包预设、MaLiLib 热键。

已经**不判**、但也不是洞的一类：数据根**里面**由用户自己摆的 junction（`mods` 指到另一个盘、
`config` 指到共享目录）。那是用户明确的安排，跟着它写是结果，不是逃逸；挡的只有
"从链接那一头读进来的东西把路径带到根外面去"。这跟"源侧链接不跟随"是同一条分工。

测试落点：`ZJ3` / `ZJ5`（锁键别名、复制实例）、`TR5`（传输不跟 junction）、`PD7`
（通用文件源侧链接）、`PF10`（MaLiLib：`config` 是 junction 时读要说清楚、写一格不穿透、
链接那一头一个字节不动）、`PL10`（数据包：`saves/<世界>/datapacks` 是 junction ⇒ 拒绝，
也不改落到 `datapacks-pending/`）、`MultiMC`（专用库：`<数据根>/libraries` 是 junction ⇒
拒绝，链接那一头收不到东西）。四道写入口现在都有判据了。


## 复制实例：先暂存，再发布

`VersionManager::copyInstanceFrom()` 不再直接往 `versions/<新名字>` 里拷。整棵树先落到同卷的
`versions/.wtfml-staging/<uuid>`，jar / json / `wtfml.meta` 都在暂存里改好，最后才一次改名发布。
理由是慢盘上的窗口：拷几 GB 要几分钟，这期间用户（或另一份启动器）完全可能在目标名字下放了
东西；旧写法失败时按 `destDir` 清理，会把对方刚写的内容一起删掉。现在：

- 失败只清本次自己的暂存；目标位置一个字节都不碰，半成品也不会出现在实例列表里；
- 发布前重新问一次目标名字；已被占用就失败并清暂存，不覆盖、不删除对方目录；
- 暂存层没有顶层 jar / json，`installedVersions()` 不会把它当成实例列出来；
- 暂存父目录若是 junction / symlink 直接拒绝，和"源侧链接不跟随"同一套判据。

判据在 `ZJ5`：正常复制后暂存层收掉；源里有 junction 时失败且不发布；拷树期间另一份创建同名
目录时发布失败、用户文件原样保留、暂存清掉。

## 破坏性操作交互矩阵

同一实例的删除、快照、备份、还原、复制/迁移与文件页改动，按“先拒绝、再重检、最后才动盘”排：

| 同时发生的事 | 拒绝/重检方式 | 回归位置 |
| --- | --- | --- |
| 游戏正在运行 | 删除、世界备份/还原、快照、还原实例、文件页启用/禁用/删除都先问运行状态；关窗另有确认 | T35、T43、T20.10 |
| 另一项文件操作在跑 | 控制器 `busy()` + `installingVersionIds()`；文件页宿主回调拒绝；批量文件页操作登记实例；快照确认框关闭后重检；世界备份开始前拒绝 | T35.2b、T20.10、T20.10b、ZJ5 |
| 外部程序改了文件 | 备份冻结字节后重扫清单；还原发布前重扫目标；不一致就停在发布前 | ZQ4、ZQ8、ZQ10 |
| 磁盘空间不足 | 备份/还原先算空间；升级有 `spaceBudgetBytes`；不足时不动盘 | ZQ8、InstanceUpgradeChecks |
| 权限/只读失败 | 删除先摘只读位再试；写入失败如实报错而不假装成功 | ZAN1、ZAN2、ZQ4 |
| 改名失败/目标被占用 | 复制先暂存，发布改名失败只清暂存；替换目标前再次检查 | ZJ5、PL10 |
| 关键发布阶段中断 | 备份/还原/升级/数据包替换都有登记或活动锁，恢复只处理能对上归属的现场 | ZQ10、ZQ11、PL10、InstanceUpgradeChecks |

这张矩阵是“已有实现 + 对应回归”的核对结果；真实慢盘、杀毒实时扫描和发布机双窗口仍需按
[docs/TESTING.md](TESTING.md) 的人工探针复跑，不能用临时目录夹具代替。

## 世界导入

存档页面的导入在后台复制，目标实例在完成前不能启动或处理其它文件操作。
页面可以关闭，完成回调不会访问已经销毁的页面。

文件先写入 saves 内独立暂存目录，完成后才改名成正式世界；已有同名世界绝不覆盖。
隐藏文件保留，源链接拒绝跟随，源世界不删除。失败会清理本次暂存，并在清理失败时说明位置。
后台复制每 1 MiB 检查停止条件，整项预算 600 秒；关闭控制器时请求停止。
任务中心那一项提供「取消」：按下后协作式停下，没拷完的暂存会被清理，账本记成「已取消」
而不是失败、也不弹失败提示；取消晚于发布则照实报成功（存档确实已经在那儿了）。
外部程序不要在导入期间修改源世界；此复制不是文件系统快照。

## 世界删除

用户在确认框里点过「删除」之后，整棵目录树才在工作线程里删（junction / 符号链接不跟随）；
删除期间该实例记进「文件操作中」，不能启动或再做其它文件操作。删除不提供取消：删到一半
停下留下的是半截世界，比删完更难收拾。删不干净时照实报失败（原话仍指向"多半是被游戏占着"），
不假装成功、也不替用户清理剩下的内容。页面可以在删除期间关闭，完成回调不会访问已销毁的页面。

## 创建备份时关闭窗口

创建世界备份和实例快照会把关闭取消传给目录扫描、分块哈希和打包进程。
打包等待每 100 ms 检查停止条件，停止子进程后清理本次不完整归档；不删除已有归档。
控制器发起的创建备份和还原整项预算均为 600 秒。文件系统读取仍是协作式取消，不能保证故障磁盘的
系统调用立即返回。还原的停止条件**只在挪走「现在这一份」之前**生效（读清单、空间检查、安全快照
这一步；刚做出来的安全快照会删掉）；一旦开始替换目录就必须走完——停在那儿会让用户既没有旧的
那一份、也没有新的这一份。不强杀线程。
